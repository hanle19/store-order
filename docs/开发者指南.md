## 0. 关于本系统

一套面向**实体门店（零售 / 批发 / 家居建材 / 通用门店）**的全链路经营管理系统。覆盖从「客户跟进 → 开单 → 进货 → 备货 → 送货 → 签收 → 财务 → 售后」的完整闭环，并附带日报、知识库、经营分析、企业微信推送等门店常用能力。

**它不是某个品类的专属系统**（代码里没有任何"床/沙发/螺丝"之类的品类限定），商品、客户、订单、促销都是**通用模型**，你拿去开便利店、服装店、五金店都能直接用。

```

        │ 生产构建产物 client/dist                │ server/public (静态托管)
```

| 层 | 技术 | 说明 |

## 二、环境要求与快速开始

### 环境要求
- **Node.js ≥ 18**（仓库自带便携版 `nodejs/`，无需单独安装；也可用自己的 Node）
- 操作系统：Windows / macOS / Linux 均可；生产推荐 Docker

### 2.1 本地一键启动（Windows）
双击根目录 **`启动系统.bat`**：它会释放 3333 端口 → 安装依赖（若缺失）→ 构建前端（若缺 `server/public/index.html`）→ 拉起后端 → 自动打开浏览器。

- 访问：`http://localhost:3333`
- 默认账号：`admin` / `admin123`

### 2.2 手动启动（跨平台）
```bash
# 后端
cd server
npm install
PORT=3333 node src/index.js

# 另开一个终端跑前端 dev（带 /api 代理到 3333）
cd client
npm install
npm run dev          # http://localhost:5173
```
前端 dev 服务器已配置 `proxy: { '/api': 'http://localhost:3333' }`，所以开发时前端直接调相对路径 `/api/...` 即可。

### 2.3 Docker 部署（飞牛 NAS / 服务器）
```bash
docker compose up -d --build
# 映射端口 3333，数据卷 ./data -> /app/data
```
`docker-compose.yml` 已设 `JWT_SECRET`、`LANG=C.UTF-8`；`Dockerfile` 为多阶段构建（先构建前端、再装生产依赖、最后拷贝 `dist` 到 `public`）。

通过 `GET/PUT /api/config` 读写。种子键包含：
`site_name, store_name, store_address, store_phone, store_logo, primary_color, industry, setup_completed, promo_enabled, promo_coupon_enabled, promo_bundle_enabled, external_coupon_reduce, break_even_margin(默认0.4), low_stock_threshold(默认5), warehouses(JSON 数组), holidays_json, contract_terms` 等。

### 5.2 设计要点（二次开发必读）
- **在途量 = 派生值**：`order_items` 中 `product_type='order'` 且订单未签 / 未完成的求和。
- **三价模型**：`cost_price`（进价）/ `price`（售价）/ `break_even_price`（= 进价 ÷ (1 − 利润率)，`break_even_margin` 默认 0.4）。多规格每规格自带三价。
- **进价落快照**：订单成交时的进价写进 `order_items.cost_price`（财务读此，不读商品当前进价）。
- **库存双写**：所有库存变动走 `stock.js` 的 `adjustStock` / `adjustVariantStock`，自动双写 `products.stock` 与流水。订货（`product_type='order'`）**不核减**现货库存；样品 / 赠品成交**才减**现货。
- **部分唯一索引**：`monthly_targets` 门店级目标用 `UNIQUE(year,month,store_id,user_id)` + 部分唯一索引 `... WHERE user_id IS NULL`，解决「UNIQUE + NULL 不互斥」问题。新增类似表务必照此模式。

## 六、后端开发指南

### 6.1 启动流程（`src/index.js`）
1. 确保 `uploads/` 存在 → 配置 CORS（默认本地白名单）→ gzip → JSON body（10mb）→ 请求日志中间件
2. 挂载 `/uploads` 静态资源
3. `initDb()`：建表 + 幂等列补丁 + 调用 `runMigrations(db)`
4. 注册健康检查 `/api/health` 与各路由（**顺序见 6.2**）
5. 静态托管 `server/public` + SPA fallback（非 `/api`、非 `/uploads` 返回 `index.html`）
6. 全局错误处理中间件 + `unhandledRejection` / `uncaughtException` 落日志
7. `startAutoBackup()` 后 `app.listen(PORT,'::')`

### 6.2 路由挂载顺序（铁律）
`index.js` 中 `aftersales.js` **必须**在 `orders.js` 之前 `app.use('/api/orders', ...)`。原因：aftersales 定义了单段字面路由 `/api/orders/returns` 与 `/api/orders/aftersales`（全局看板），若 orders 在前，其 `GET /:id` 会贪婪匹配把 `returns` 当成订单 id，导致全局列表接口不可达。**新增路由时务必注意贪婪 `/:id` 的遮蔽问题**。

### 6.3 中间件
- `authMiddleware`（`middleware/auth.js`）：支持 `Authorization: Bearer <token>`；**仅 GET** 允许 `?token=` 传参（合同 / 送货单打印等无法带 Header 的场景）。缺失 → 401；过期 → 401。结果挂到 `req.user`。
- `roleMiddleware(...roles)`：检查 `req.user.role ∈ roles`，否则 403。
- 登录限流：`auth.js` 内置进程内 Map，同用户名 + IP 连续 5 次失败锁 10 分钟（重启清零，不落库）。
- `requestLog`：按天轮转 JSON Lines 落 `server/logs/`，token/password/secret 自动掩码。

### 6.4 鉴权与多店隔离（`utils/storeScope.js`）
收口在 `storeScope.js`，已覆盖 14+ 文件。核心 API：
- `resolveStoreIds(req)`：sales → 仅自身 `store_id`（无则 `[]`，调用方用 `1=0` 兜底）；admin/boss → `?store_id=` 限定或全部门店。
- `storeClauseAndParams(req, alias='o')`：返回 `{ clause:' AND <alias>.store_id IN (?)', params }`；ids 为空时返回 ` AND 1=0`。
- `appendStoreFilter(where, params, alias, req)`：自动追加门店过滤。
- `resolveWriteStoreId(req)`：写操作落店（sales 用自身店；admin/boss 用 `body.store_id`）。

> 🔴 **别名铁律**：`storeClauseAndParams(req, 'd')` 对 **admin 也返回 ` AND d.store_id IN(...)`**（admin 看全店，不是空 clause）。因此 SQL 主表**必须起与 alias 完全一致的别名**，否则拼出 `d.store_id` 报 `no such column`。曾因此导致 `delivery.js` 签收 / 回退一直 500。

### 6.5 数据访问约定（better-sqlite3）
- **防注入**：表名 / 列名用白名单（不要用用户输入拼 SQL）；**值一律用 `?` 占位符**。
- **LIMIT 钳制**：凡 `LIMIT ?` 必须同时钳上下限，用 `Number.isFinite(raw)&&raw>0?raw:default`（`parseInt(x)||20` 对负数失效）。
- 🔴 **负 LIMIT = 不限制**：`LIMIT -1` 实测返回全表，所以绝不能把未校验的负数直接喂给 `LIMIT`。所有分页上限已钳到 200。
- 单引号：SQL 字符串用单引号。
- 事务：跨表写操作包在 `db.transaction(...)` 中。
- Prepared statement 缓存：`stock.js` 用 `WeakMap<db, Map<key,stmt>>` 复用。

### 6.6 收口模块（不要重复造轮子）
- **库存**：`stock.js` 的 `adjustStock` / `adjustVariantStock` / `syncProductStockFromVariants`。
- **价格 / 金额 / 券对账**：`services/orderPricing.js`（`buildItemPricing` 收口取价）。
- **出库 / 退回 / 反查**：`services/orderInventory.js`。
- **成交推进 / 自动建档**：`services/orderCustomer.js`。
- **审计**：`utils/audit.js` 的 `logAudit` / `auditFromReq` / `auditDelete` / `auditUpdate`。**失败旁路**（审计挂了不拖垮业务）。删除类操作请在 handler 内调用 `auditDelete`，类型白名单未登记会降级为 `'other'`，`details` 超过 8KB 自动截断。
- **聚合缓存**：`utils/aggCache.js`，数据指纹 + 角色 + 用户 + 门店 + 年月 + 60s TTL；dashboard / analytics 已接入；恢复出厂 / 备份还原自动 clear。

### 6.7 版本化迁移（`utils/migrations.js`）
新增表结构变更（改 CHECK、重建表、订正数据）请走迁移，**不要**直接改 `db.js` 的 `initDb`：
```js
// migrations.js 内追加一项
{
  version: 3,
  name: 'add_xxx_table',
  up: (db) => {
    db.exec(`CREATE TABLE IF NOT EXISTS xxx (...)`);
    return true; // 已生效
  },
  // 自检幂等：已生效返回 false，避免重复执行
}
```
- `runMigrations` 按 `version` 递增执行；`BASELINE_VERSION=1`。
- 🔴 重建表必须**在事务外**关闭 `foreign_keys`（事务内该 pragma 是 no-op）；AUTOINCREMENT 表重建后要补 `sqlite_sequence`。
- 🔴 **迁移失败 = 直接中止启动**（`throw`），绝不留半新半旧结构。

### 6.8 自动备份与日志
- `utils/backup.js`：收口备份（`createBackupZip` / `verifyBackupZip` / `safeRemove` / `listBackupFiles`），手动与自动共用一种格式（还原接口只认一种）。
- `utils/autoBackup.js`：启动 20s 检查 → 今日无备份则补备；每天 `AUTO_BACKUP_HOUR` 后执行；保留 `AUTO_BACKUP_KEEP` 份；备份后校验，缺 `store.db`/`manifest` 即作废。
- `middleware/requestLog.js`：落 `server/logs/access-YYYY-MM-DD.log` 与 `error-*`；接口 `GET /api/system/logs`（admin）。
- 前端入口：「系统设置 → 系统与数据 → 系统维护」页顶部两张卡（`AutoBackupCard` / `SystemLogsCard`）。

## 八、前端开发指南

### 8.1 入口与 Provider（`main.jsx`）
按顺序嵌套：`ThemeProvider → BrandProvider → AntApp → BrowserRouter → AuthProvider → StoreProvider → CartProvider → App`。
- `ThemeProvider`：亮 / 暗主题切换（`isDark` 存 localStorage）。
- `BrandProvider`：拉取 `/config`（有 token）或 `/config/public`，注入 antd `colorPrimary`，并把主色派生色写到 CSS 变量（支持初始化向导改主题色）。
- `AuthProvider`：从 localStorage 恢复 user；启动时用 `/auth/me` 校验 token 有效性。
- `StoreProvider` / `CartProvider`：当前门店、开单购物车状态。

### 8.2 路由表与权限（`App.jsx`）
页面均为 `React.lazy` 懒加载，外层包 `RouteErrorBoundary`（单页崩溃不影响整树）。守卫：
- `PrivateRoute`：无 token 跳 `/login`。
- `RoleRoute allow={['admin','boss']}`：sales 被重定向到 `/daily`。
- 登录落地：sales → `/daily`，其余 → `/dashboard`。

页面清单（节选）：`Dashboard`(admin/boss) · `Shop`(开单) · `Orders`/`OrderDetail` · `Products`(admin/boss) · `Inventory`(admin/boss) · `Purchases` · `Finance`(admin/boss) · `KnowledgeFeed`/`Detail`/`Admin`/`Editor` · `DailyReport` · `CustomerManagement` · `Analytics`(admin/boss) · `Settings`(admin) · `AftersalesSection` · `BundleManagement` · `CouponManagement` · `DeliveryPersons` · `MonthlyTargets` · `StoreManagement` · 等等（共约 50 个页面文件）。

### 8.3 API 客户端（`api.js`）
```js
import api from '../api';
const res = await api.get('/customers', { params: { page:1, pageSize:20 } });
const data = res.data; // 后端直接返回数据体
await api.post('/orders', payload);
```
- 自动从 localStorage 带 `Authorization: Bearer <token>`。
- 响应拦截：401 自动清 token / user 并跳 `/login`。
- **响应结构**：大部分接口直接返回数据对象（如 `{ data: [...] }` 或 `{ list, total }`），具体以各接口实际返回为准；失败为 `{ error }`。

### 8.4 设计系统（令牌）
- **所有颜色令牌集中在 `client/src/index.css` 的 `:root` 与 `html[data-theme="dark"]`**，其余一律 `var(--token)`。

## 九、二次开发实战：从零加一个模块

下面以「门店公告 `notices`」为例，**完整演示后端 → 数据库 → 前端 → 菜单**四步。复制这套模板即可套用到任何新业务。

### 第 1 步：建表（`db.js` 的 `initDb` 内追加）
```js
db.exec(`CREATE TABLE IF NOT EXISTS notices (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  content TEXT,
  pinned INTEGER DEFAULT 0,
  store_id INTEGER DEFAULT 1,
  created_by INTEGER,
  created_at TEXT DEFAULT (datetime('now','localtime'))
)`);
// 多店隔离索引
db.exec(`CREATE INDEX IF NOT EXISTS idx_notices_store ON notices(store_id)`);
```

### 第 2 步：后端路由（`server/src/routes/notices.js`）
```js
import express from 'express';
import { getDb } from '../db.js';
import { authMiddleware, roleMiddleware } from '../middleware/auth.js';
import { auditFromReq } from '../utils/audit.js';
import { storeClauseAndParams, appendStoreFilter } from '../utils/storeScope.js';

const router = express.Router();
router.use(authMiddleware); // 全部需登录

// 列表（按店隔离）
router.get('/', (req, res) => {
  const db = getDb();
  const { clause, params } = storeClauseAndParams(req, 'n'); // 别名 n
  const rows = db.prepare(`SELECT * FROM notices n WHERE 1=1 ${clause} ORDER BY pinned DESC, id DESC`).all(...params);
  res.json({ list: rows });
});

// 新增（仅 admin/boss）
router.post('/', roleMiddleware('admin','boss'), (req, res) => {
  const db = getDb();
  const { title, content, pinned=0, store_id } = req.body;
  const sid = store_id || req.user.store_id || 1;
  const info = db.prepare('INSERT INTO notices (title,content,pinned,store_id,created_by) VALUES (?,?,?,?,?)')
    .run(title, content, pinned?1:0, sid, req.user.id);
  auditFromReq('notice', info.lastInsertRowid, 'create', req, { title });
  res.json({ id: info.lastInsertRowid });
});

// 删除（仅 admin）
router.delete('/:id', roleMiddleware('admin'), (req, res) => {
  const db = getDb();
  db.prepare('DELETE FROM notices WHERE id=?').run(req.params.id);
  auditFromReq('notice', req.params.id, 'delete', req);
  res.json({ ok: true });
});

export default router;
```
> 注意：`storeClauseAndParams(req,'n')` 返回的 clause 里用的是 `n.store_id`，所以 SQL 主表必须起别名 `n`。

### 第 3 步：注册路由（`index.js`）
在合适位置加入：
```js
import noticeRoutes from './routes/notices.js';
// ...
app.use('/api/notices', noticeRoutes);
```

### 第 4 步：前端页面 + 菜单
新建 `client/src/pages/Notices.jsx`（参考 8.7 结构），并在 `App.jsx` 的 `<Route>` 树与 `Layout.jsx` 的侧边栏菜单里加上入口：
```jsx
<Route path="notices" element={<WithErrBoundary><RoleRoute allow={['admin','boss']}><Notices /></RoleRoute></WithErrBoundary>} />
```
侧边栏加一项 `{ key:'/notices', label:'门店公告', icon:<NotificationOutlined /> }` 即可。

**完成。** 重启后端（加载新路由 + 建表），刷新前端（重新构建或 dev），就能用了。

## 十、运维与部署

### 10.1 备份 / 恢复 / 复位（全部 `role(admin)`）
- **一键备份** `POST /api/system/backup`：打包 `store.db` + `uploads/` + `manifest.json`，浏览器下载 zip。
- **一键恢复** `POST /api/system/restore`：上传 zip → 校验（zip-slip 防护）→ 恢复前自动备份到 `pre-restore-*.zip` → 原子替换主库 + uploads → 强制重登。
- **恢复出厂** `POST /api/system/reset`：清空全部业务表 + 重置配置 + 删导购账号，只留 admin（需输入「确认重置」，不可逆）。
- **自动备份**：每日 `AUTO_BACKUP_HOUR` 后执行，保留 `AUTO_BACKUP_KEEP` 份；可经 `GET /api/system/auto-backup/status` 查看、`POST /api/system/auto-backup/run` 立即触发。

### 10.2 升级与迁移
- 拉新代码后**重启后端**，`initDb` 幂等建表、`runMigrations` 自动跑迁移。
- 跨大版本升级前请先**一键备份**。

### 10.3 日志与排错

## 十一、约定与踩坑（必读，能省你几小时）

1. 🔴 **改后端必须重启** `src/index.js` 才加载（生产靠「启动系统.bat」）。
2. 🔴 **构建用 `node build-safe.mjs`**（仓库根目录）：它固化「移走旧产物 → vite build → 回拷 `client/dist` 到 `server/public`」三步。手工分步易漏 `cp` 导致生产 500。生产静态文件从 `server/public` 提供，不是 `client/dist`。
3. 🔴 **路由挂载顺序**：`aftersales.js` 必须在 `orders.js` 之前；小心贪婪 `/:id` 遮蔽字面路由（如 `/returns`、`/meta/dicts` 必须定义在 `/:id` 之前）。
4. 🔴 **storeScope 别名铁律**：`storeClauseAndParams(req,'d')` 对 admin 也返回 ` AND d.store_id IN(...)`，SQL 主表必须起一致别名。
5. 🔴 **负 LIMIT = 不限制**：`LIMIT ?` 必须钳上下限（上限 200），别把未校验的负数喂给 LIMIT。
6. 🔴 **SQLite 字符串用单引号**，不用双引号。
7. 🔴 **颜色门禁**：新增前端样式不得出现裸 `#hex`，用 `index.css` 的令牌；提交前跑 `node scripts/check-hardcoded-colors.mjs`。
8. 🟠 **JWT 密钥**：生产务必通过 `JWT_SECRET` 环境变量显式设置；未设置会自动生成并持久化到 `server/.jwt_secret`，重启不变。
9. 🟠 **CORS**：默认仅本地白名单；部署到其他域名 / 飞书内嵌 / 公网，用 `CORS_ORIGINS` 显式指定。
10. 🟠 **审计是旁路**：调用 `auditDelete` 等失败不会拖垮业务，但请确保删除类操作都有审计调用。
11. 🟠 **下载托管**：上传文件经 `/uploads` 对外提供，后端读 `uploads/` 目录时务必做路径校验（参考 `system.js` 的 zip-slip 防护）。
12. 🟡 **前端入口**：`store-order` 实际部署代码在 `Downloads/store-order`（或你克隆的仓库），工作区里的旧副本不部署，请勿改。

## 十二、常见问题 FAQ

**Q：默认管理员密码是多少？**
A：`admin / admin123`。生产请立即改密码（`/api/auth/change-password` 或系统设置）。

**Q：怎么改主题色 / 店名？**
A：系统设置 → 品牌与单据（初始化向导首次进入也会引导）。配置落在 `system_config`，前端 `BrandContext` 自动派生主色并覆盖 CSS 变量。

**Q：sales 能看到别的店数据吗？**
A：不能。`storeScope.js` 强制按 `store_id` 隔离；`sales` 仅自身门店与自己名下订单 / 客户。

**Q：加了一个接口但前端调不到？**
A：① 后端是否重启？② `index.js` 是否 `app.use` 注册？③ 是否被贪婪 `/:id` 遮蔽（调整挂载顺序或路由路径）？④ 跨域是否放行（看 `CORS_ORIGINS`）？

**Q：订单删除报错 409？**
A：该订单已关联退换单 / 售后单，需先处理关联单再删（或标记取消）。

**Q：Docker 部署后数据在哪？**
A：卷 `./data` 映射到容器 `/app/data`，即 `store.db` 所在。备份 / 恢复走系统设置，或直接备份该目录。

**Q：如何二次开发最稳？**
A：先读完第九章的「公告模块」模板，照着「建表 → 路由（带 storeScope + 审计）→ 注册 → 前端页面 + 菜单」四步走，每加一个接口就手测一次。
